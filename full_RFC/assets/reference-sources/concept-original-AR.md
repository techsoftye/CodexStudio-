# Codex Studio

### A Project-Centric Development Workspace

**نوع الوثيقة:** ملخص مفهوم المنتج والفهرس المرجعي للمقترح (Product Concept & Outline)  
**الحالة:** مسودة للنقاش — بانتظار الاعتماد والتوجيهات

**التاريخ:** 17 أكتوبر 2026  
**الجهة المستهدفة:** فرق المنتج والهندسة وتجربة المطورين لدى OpenAI ومجتمع المطورين

## أولًا: ملخص الموضوع (Concept Summary)

### الفكرة

**Codex Studio** مقترح لتقديم **بيئة عمل مكتبية هندسية متمحورة حول المشروع البرمجي**، تستفيد من قدرات Codex القائمة وتعيد تنظيمها في تجربة موحدة ومستمرة للمطور. ينتقل محور العمل من سجل المحادثات المنفصلة إلى **المشروع** بوصفه مساحة تربط المحادثات والمهام والقرارات والقواعد والنتائج والملفات والوكلاء.

الفكرة **ليست تطوير نموذج ذكاء اصطناعي جديدًا، ولا إعادة بناء وظائف Codex الحالية من الصفر، ولا مجرد إضافة تبويبات**. بل هي تصور لتجربة منتج متخصصة تعيد استخدام البنية والقدرات القائمة حيثما أمكن، وتضيف روابط منظمة وواجهات وسير عمل تكملها.

### لماذا هذا المقترح؟

تزداد أهمية الوكلاء القادرين على فحص المستودعات وتنفيذ التغييرات واختبارها. لكن إدارة مشروع طويل الأمد تتطلب أكثر من محادثات قابلة للاستئناف: يجب أن تكون **المهام، والقرارات المعتمدة، وقواعد المشروع، ونتائج التشغيل، والمصادر** سهلة الاكتشاف والتتبع عبر الجلسات. يهدف المقترح إلى تقليل إعادة شرح المتطلبات، وتشتت المعرفة، والتنقل المتكرر بين الأدوات، مع إبقاء المطور صاحب القرار النهائي.

### الرؤية

أن يصبح **Codex Studio شريك عمل هندسيًا يوميًا** للمطور؛ بيئة تُستخدم لتخطيط التطوير، وتوجيه الوكلاء، وتتبع التنفيذ، ومراجعة ما تحقق، والعودة إلى سياق المشروع بثقة. تستهدف التجربة مستوى تنظيم قد يجعلها ضمن أدوات التطوير الأساسية للمستخدمين، دون الادعاء مسبقًا أنها ستستبدل IDEs القائمة أو تحقق مكاسب كمية مثبتة.

### نطاق المنتج وتموضعه

- **المقترح الأساسي:** تجربة/تطبيق مكتبي متخصص للمطورين باسم *Codex Studio*.
- **الخيار المعماري البديل الواجب تقييمه:** مساحة هندسية مستقلة وظيفيًا داخل التطبيق المكتبي الموحد، إذا كان ذلك أكثر جدوى في ضوء اتجاه المنتجات الحالي.
- **التكامل بدل التكرار:** الاستفادة من Codex، وCodex CLI، والمستودعات وGit، وSkills، وملفات `AGENTS.md` والتكامل مع IDEs؛ مع التحقق من تفاصيل الدعم الحالية عند كتابة الوثيقة الكاملة.
- **نطاق العرض:** تظهر أدوات المساحة الهندسية في **سياق المشروع**، لا في المحادثات العامة.
- **المنفعة المقصودة:** تحسين التنظيم والاستمرارية والإشراف والإنتاجية، لا الادعاء بأن جميع الوظائف غير متوفرة حاليًا.

### الواجهة الرئيسية المعتمدة مبدئيًا

`Chat | Tasks | Decisions | Results | Library | More`

| التبويب | الدور العملي |
|---|---|
| **Chat — المحادثة** | التواصل مع Codex داخل المشروع، وصياغة الطلبات والخطط، وتحويل مخرجات النقاش إلى عناصر منظمة. |
| **Tasks — المهام** | إدارة المهام وفق حالات `Todo / Active / Review / Done / Deferred`، مع مراحل المشروع (Stages) وأقسامه (Sections) والمهام الأب والمواعيد الاختيارية. |
| **Decisions — القرارات** | توثيق واعتماد القرارات الهندسية والوظيفية، وحفظ أسبابها وتاريخ استبدالها وربطها بالعمل. |
| **Results — النتائج** | تتبع نتائج كل عملية تنفيذ، بما في ذلك التغييرات والاختبارات والأدلة والمخرجات وإجراءات المراجعة وإعادة التشغيل. |
| **Library — المكتبة** | ملفات المشروع والجلسات عبر `Project Files / Session Files`، مع البحث والفلاتر حسب نوع الملف، والمعاينة، والربط بالعناصر. |
| **More — المزيد** | الوظائف والسجلات المتخصصة الأقل استخدامًا، التي تُحدد وفق حاجة المنتج دون إثقال الشريط الرئيسي. |

**السياقات الجانبية تتغير حسب التبويب:** في Chat تظهر مصادر العمل وسياق المحادثة؛ في Tasks تظهر **Stages / Sections** وملخص السياق الحالي، ويُفتح نموذج New Task في اللوحة اليمنى كعرض فرعي بزر رجوع؛ وفي Decisions تظهر **Project Rules** باللوحة اليمنى مع إمكانية إرجاعها إلى مصدرها مثل `AGENTS.md`. وفي Library يمكن عرض مصادر خارجية **اختيارية** بحسب ما يتوفر من تكاملات وصلاحيات فعلية، وليس باعتبارها مدعومة تلقائيًا.

### مبادئ تصميمية ملزمة أثناء تطوير المقترح

1. **Project-first:** المشروع أصل التنظيم؛ المحادثات والمهام والقرارات والنتائج كيانات مترابطة داخله.
2. **Reuse before rebuild:** عدم إعادة تقديم وظائف Codex القائمة على أنها ابتكارات جديدة؛ توضيح الإضافة والاختلاف بدقة.
3. **Practical over decorative:** واجهات خفيفة قابلة للاستخدام اليومي، لا لوحات معلومات ضخمة لمجرد العرض.
4. **Human oversight:** لا يُعتمد قرار هندسي أو تُغيَّر قاعدة حساسة دون آلية مراجعة وإقرار واضحة.
5. **Traceability:** ربط المهمة بمصدر الطلب والقرار وأدلة التنفيذ والملفات الناتجة.
6. **Context discipline:** فصل سياق المشروع عن سجلات التنفيذ المطولة، واسترجاع المعلومات اللازمة انتقائيًا؛ التوفير في الموارد **فرضية تحتاج إلى قياس**.
7. **Compatibility:** الحفاظ على تدفقات Codex الحالية والتكاملات القائمة ما أمكن، مع تجنب تحويل المقترح إلى بديل إلزامي عن VS Code أو Git أو أدوات إدارة المشاريع.
8. **Evidence-based claims:** التمييز في الوثيقة النهائية بين *متاح حاليًا* و*مقترح* و*يتطلب تحققًا*، مع مراجع رسمية.

### مخرجات النشر المقترحة (بعد الاعتماد)

- **Executive Brief:** ملخص إنجليزي قصير للمراسلات المهنية.
- **Full Product Concept RFC:** وثيقة تفصيلية بالتصاميم والمقارنات والمراجع والمخاطر ومؤشرات التحقق.
- **OpenAI Community Topic:** منشور إنجليزي مركز بصور مختارة ورابط الوثيقة الكاملة، دون محاولة إدراج كل التفاصيل في متن المنشور.

> **الرسالة المركزية:** *Codex Studio is not another layer of project-management features. It is a proposal for a focused, project-centric engineering experience that connects the work developers already do with Codex—planning, decisions, execution, evidence, and persistent project knowledge—into a coherent workspace.*

## رابعًا: نقاط معتمدة وحدود هذه المسودة

**المعتمد مبدئيًا:** اسم عمل *Codex Studio*، التوجه المتمحور حول المشروع، التبويبات الستة، فكرة اللوحة اليمنى السياقية، الفصل بين Tasks وDecisions وResults وLibrary، وإعادة استخدام قدرات Codex المتاحة.

**ما يزال مفتوحًا:** القرار النهائي بشأن استقلال التطبيق، تفاصيل التنفيذ التقنية، تقديرات التكلفة والجدول الزمني، التكاملات الخارجية المسموحة، وصياغة الادعاءات والمراجع النهائية. كما يُراجع توفر الاسم وتعارضه المحتمل مع مشاريع أخرى قبل النشر الرسمي.

**الخطوة التالية:** انتظار الملاحظات والتعليمات قبل الشروع في كتابة فصول المقترح أو تحويله إلى منشور إنجليزي.
