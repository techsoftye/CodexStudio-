    Historical review record (supplied with RFC v1.1). This records checks performed for the author’s earlier archive. The current repository packaging checks are recorded separately in publication validation. Brand spelling and navigation may have been normalized for this publication package.

    Requirement coverage / تغطية المتطلبات

    Each requirement has a local acceptance criterion. V-cases are representative product test cases, not executed tests. Local criterion means the requirement text supplies the acceptance procedure. Expansion requirements apply only to their selected post-MVP capability (Table 12-4); they are not all G1 gates.

    Requirement Scope Primary chapter Representative V-case Acceptance criterion
    R-02-01 Core or stated gate / أساسي أو بوابة محددة 02 / AR Local criterion Claim traceability. Every assertion of current capability MUST map to an official source and verification date. Acceptance: a reviewer can follow each Appendix B baseline row to Appendix E; unsupported guarantees remain classified Requires Validation. Proposed behavior must never acquire Existing status because it appears in a convincing mockup.
    R-03-01 Core or stated gate / أساسي أو بوابة محددة 03 / AR Local criterion Honest problem evidence. The evaluation MUST separate self-reported friction from observed task errors and measured time. Acceptance: the study dataset identifies its evidence type and does not report the illustrative scenario or mockup values as participant results. If participants already recover state reliably and quickly, reduce or reject the corresponding product claim.
    R-04-01 Core or stated gate / أساسي أو بوابة محددة 04 / AR Local criterion Project continuity. All structured records MUST carry their owning Project identity, or explicit Group identity for group-owned coordination records, and cross-project access MUST be checked even when a link is known. Acceptance: opening a record from a different project cannot silently change the active execution target or reveal inaccessible content.
    R-04-02 Core or stated gate / أساسي أو بوابة محددة 04 / AR V-01 Optional structure. A title-only task and an ordinary conversation MUST remain valid entry points. Acceptance: a user can ask a question without a task, and create a task without Stage, Section, Parent Task, Due Date, Skills, or attachments.
    R-04-03 Core or stated gate / أساسي أو بوابة محددة 04 / AR Local criterion Reuse with accountability. Studio SHOULD use a supported Codex integration while owning its own record consistency and review semantics. Acceptance: the architecture review identifies which component owns every persistent record and failure response; no private OpenAI service or undocumented database is assumed.
    R-04-04 Expansion / توسع 04 / AR V-13 Explicit umbrella boundary. A Project Group MUST preserve member-project identity, environment selection and authorization. Acceptance: adding Backend and Flutter to one group neither changes their working directories nor grants either participant new repository access. Group coordination records identify their own scope rather than masquerading as project records.
    R-05-01 Core or stated gate / أساسي أو بوابة محددة 05 / AR Local criterion Switching tabs MUST preserve project identity. Start a run, switch projects, and confirm the run remains bound to its original project.
    R-05-02 Core or stated gate / أساسي أو بوابة محددة 05 / AR V-02 Task promotion MUST be editable and nonexecuting. Save selected items twice after a simulated timeout; one logical save produces one set of tasks.
    R-05-03 Core or stated gate / أساسي أو بوابة محددة 05 / AR V-01 Panels MUST follow Table 05-2. Opening and closing New Task restores the previous task filter and keyboard focus.
    R-05-04 Core or stated gate / أساسي أو بوابة محددة 05 / AR Local criterion Navigation MUST distinguish inaccessible, missing and filtered records without showing another record's content.
    R-05-05 Core or stated gate / أساسي أو بوابة محددة 05 / AR V-11 Every primary action MUST be keyboard accessible and understandable without color; verify English and Arabic at enlarged text sizes.
    R-05-06 Core or stated gate / أساسي أو بوابة محددة 05 / AR Local criterion More MUST expose diagnostics without starting work; blocking approvals must also remain visible at their source.
    R-05-07 Expansion / توسع 05 / AR V-13 Group navigation without implicit execution. Group views MUST retain originating project labels and permission-filtered counts. Acceptance: switch between Backend and Flutter, then launch; only the explicitly confirmed project/profile is targeted, and inaccessible records do not leak through search, counts or previews.
    R-06-01 Core or stated gate / أساسي أو بوابة محددة 06 / AR V-01 A task MUST save with only Title; defaults and dropdown values match Table 06-1.
    R-06-02 Core or stated gate / أساسي أو بوابة محددة 06 / AR V-02 Section/Stage and Parent Task consistency MUST be checked at save. Concurrent edits cannot create an ancestor cycle.
    R-06-03 Core or stated gate / أساسي أو بوابة محددة 06 / AR V-03 Runtime completion MUST NOT set Done. A failed attempt leaves independently meaningful task state.
    R-06-04 Core or stated gate / أساسي أو بوابة محددة 06 / AR Local criterion Done MUST identify reviewed acceptance or explicit manual completion; missing checks cannot become fictional passes.
    R-06-05 Core or stated gate / أساسي أو بوابة محددة 06 / AR Local criterion Editing task scope MUST preserve the version used by an existing attempt and signal divergence.
    R-06-06 Core or stated gate / أساسي أو بوابة محددة 06 / AR Local criterion Deferral, hierarchy changes and due dates MUST NOT silently start, stop, delete or approve execution.
    R-06-07 Expansion / توسع 06 / AR V-15 Project-local tasks and bounded assignments. A task MUST retain one project owner when linked into a Change Set. Acceptance: assigning a Backend task to a Flutter specialist without Backend authority cannot start a Backend write; changing the assignment does not reattribute an existing attempt.
    R-07-01 Core or stated gate / أساسي أو بوابة محددة 07 / AR V-03 Agent-created decisions MUST remain Proposed until an authorized human approves an exact version.
    R-07-02 Core or stated gate / أساسي أو بوابة محددة 07 / AR V-04 Supersession MUST preserve history and update the successor relationship atomically; cyclic replacements fail validation.
    R-07-03 Core or stated gate / أساسي أو بوابة محددة 07 / AR Local criterion Repository-backed rules MUST expose source and scope; editing the panel cannot silently diverge from the authoritative file.
    R-07-04 Core or stated gate / أساسي أو بوابة محددة 07 / AR V-09 Consequential unresolved conflicts MUST block affected new execution and show the conflicting sources.
    R-07-05 Core or stated gate / أساسي أو بوابة محددة 07 / AR V-04 Decision changes MUST preserve prior run context and expose affected ongoing work and review implications.
    R-07-06 Core or stated gate / أساسي أو بوابة محددة 07 / AR Local criterion Approval of a decision MUST NOT count as operation authorization or result acceptance.
    R-07-07 Expansion / توسع 07 / AR V-14 Explicit shared-decision applicability. A group decision MUST identify affected projects and preserve versioned acknowledgments. Acceptance: a Backend-only approval cannot mark Flutter integration accepted or waive Flutter's governing instructions.
    R-08-01 Core or stated gate / أساسي أو بوابة محددة 08 / AR V-05 All five state dimensions MUST remain independent. A Finished attempt with a Not Run required check stays unverified and Pending Review.
    R-08-02 Core or stated gate / أساسي أو بوابة محددة 08 / AR V-06 Review Changes MUST open the recorded snapshot or explain its unavailability; it cannot substitute today's file.
    R-08-03 Core or stated gate / أساسي أو بوابة محددة 08 / AR V-05 Counts and check states MUST be evidence-derived. A successful build cannot populate unrelated acceptance checks as Passed.
    R-08-04 Core or stated gate / أساسي أو بوابة محددة 08 / AR Local criterion Re-run MUST create a new attributable attempt and preserve earlier evidence; unknown side effects require reconciliation.
    R-08-05 Core or stated gate / أساسي أو بوابة محددة 08 / AR V-05 Acceptance MUST bind actor, exact result version and task criteria; exceptions remain visible and cannot bypass enforced policy.
    R-08-06 Core or stated gate / أساسي أو بوابة محددة 08 / AR Local criterion Additional evidence or corrected summaries MUST preserve review history and require renewed acceptance when its subject changes.
    R-08-07 Core or stated gate / أساسي أو بوابة محددة 08 / AR Local criterion Observable transitions. Attempt state MUST follow confirmed runtime events or an explicitly uncertain observation. Lost connectivity cannot establish Finished, and a rejected approval cannot be translated into an assumed cancellation without runtime evidence.
    R-09-01 Core or stated gate / أساسي أو بوابة محددة 09 / AR Local criterion Project Files and Session Files MUST remain primary views; Input/Output/Resource and type filters do not replace them.
    R-09-02 Core or stated gate / أساسي أو بوابة محددة 09 / AR Local criterion A file shared by project and session associations MUST retain one logical identity and distinguish revisions.
    R-09-03 Core or stated gate / أساسي أو بوابة محددة 09 / AR V-06 Live and historical references MUST open their stated versions; a missing historical artifact cannot fall back silently to the live path.
    R-09-04 Core or stated gate / أساسي أو بوابة محددة 09 / AR V-08 Preview and import MUST validate access and safe handling; malformed files cannot trigger executable content.
    R-09-05 Core or stated gate / أساسي أو بوابة محددة 09 / AR Local criterion Removing an association MUST NOT delete bytes; deleting retained evidence requires an explicit policy-aware action and availability record.
    R-09-06 Core or stated gate / أساسي أو بوابة محددة 09 / AR Local criterion External access MUST be scoped and revocable; unavailable providers remain unavailable rather than suggesting a working integration.
    R-09-07 Expansion / توسع 09 / AR V-13, V-17 Shared and multimodal provenance. Shared contracts and media-derived context MUST retain source/version and access scope. Acceptance: revocation removes future retrieval, an uncertain transcript stays uncertain, and a visual claim links to the captured frame or declares its absence.
    R-10-01 Core or stated gate / أساسي أو بوابة محددة 10 / AR Local criterion Every dispatched attempt MUST have a persisted manifest identifying task, source versions and inclusion modes.
    R-10-02 Core or stated gate / أساسي أو بوابة محددة 10 / AR V-09 Context budgeting MUST preserve required guidance; an oversized required set blocks or narrows scope visibly.
    R-10-03 Core or stated gate / أساسي أو بوابة محددة 10 / AR Local criterion Superseded, held or inaccessible material MUST NOT silently govern new work; test stale links and revoked access.
    R-10-04 Core or stated gate / أساسي أو بوابة محددة 10 / AR V-04 Changes during execution MUST produce drift or steering records without modifying the original manifest.
    R-10-05 Core or stated gate / أساسي أو بوابة محددة 10 / AR V-12 Concurrent contributions MUST retain separate lineage; integration success requires evidence for the combined snapshot.
    R-10-06 Core or stated gate / أساسي أو بوابة محددة 10 / AR V-08 Retrieved content MUST NOT elevate its authority; an injected instruction in a file cannot approve or grant access.
    R-10-07 Expansion / توسع 10 / AR V-13 Environment identity. Every group-coordinated attempt MUST pin one Project, Environment Profile version and observed target. Acceptance: an unavailable Flutter target blocks its dependent check and never redirects it to the Backend environment.
    R-10-08 Expansion / توسع 10 / AR V-14, V-15 Combined compatibility. Group acceptance MUST bind an Integration Manifest across the required member revisions. Acceptance: Backend passing and Flutter Not Run cannot produce a verified integrated result; a subsequent contract change invalidates only the dependent assessment and preserves history.
    R-11-01 Core or stated gate / أساسي أو بوابة محددة 11 / AR Local criterion Every persistent entity and external reference MUST have a declared owner and project boundary.
    R-11-02 Core or stated gate / أساسي أو بوابة محددة 11 / AR V-07 An uncertain launch MUST NOT auto-retry; inject crashes before/after acknowledgement and prove no second dispatch occurs without reconciliation.
    R-11-03 Core or stated gate / أساسي أو بوابة محددة 11 / AR V-07 Duplicate/out-of-order events MUST preserve consistent state and auditable gaps; verify against a pinned adapter contract.
    R-11-04 Core or stated gate / أساسي أو بوابة محددة 11 / AR Local criterion Approval, operation permission and result acceptance MUST remain separate; stale approval replay is rejected.
    R-11-05 Core or stated gate / أساسي أو بوابة محددة 11 / AR V-10 Storage upgrades and evidence retention MUST have tested failure recovery and explicit availability semantics.
    R-11-06 Core or stated gate / أساسي أو بوابة محددة 11 / AR V-10 Export MUST preserve authorized relationships and hashes while excluding secrets and disallowed content.
    R-11-07 Core or stated gate / أساسي أو بوابة محددة 11 / AR V-08 Cross-project access and path escape MUST fail at the service boundary, not merely be hidden in the UI.
    R-11-08 Core or stated gate / أساسي أو بوابة محددة 11 / AR Local criterion Unsupported runtime capabilities MUST disable or degrade the dependent workflow explicitly; no private database dependence.
    R-11-09 Expansion / توسع 11 / AR V-16 Identity and least privilege. Every delegated execution MUST identify its agent instance, authenticated principal, accountable human and grant. Acceptance: a coordinator cannot grant a child access the coordinator lacks.
    R-11-10 Expansion / توسع 11 / AR V-16 Separate assignment and acceptance. Assignment MUST NOT grant access or bypass independent review. Acceptance: a review agent's favorable assessment cannot produce human Accepted status; the same author principal fails a configured independent-review gate.
    R-11-11 Expansion / توسع 11 / AR V-16 Revocation and audit. Expired/revoked grants MUST prevent new authorized actions, with an explicit limitation for already-issued credentials and ongoing work. Audit actor, principal, delegator, policy/grant revision, target and decision outcome without storing secrets.
    R-11-12 Expansion / توسع 11 / AR V-17 Modality-independent authority. Voice/image inputs MUST obey the same scoped permissions and exact-action confirmation as text. Acceptance: an instruction visible in an image, uncertain transcript or replayed approval cannot authorize a write.
    R-11-13 Expansion / توسع 11 / AR V-18 Specialist evidence boundaries. Domain adapters MUST distinguish simulation, physical-device execution and quantum-provider execution. Acceptance: a simulator report cannot be labeled hardware validation, and provider cost or actuation is never authorized by a research request alone.
    R-12-01 Core or stated gate / أساسي أو بوابة محددة 12 / AR Local criterion Complete narrow delivery. G1 MUST demonstrate one end-to-end workflow including failure and recovery, with every MVP cell in Table 12-2 represented. An attractive mockup or isolated successful run is insufficient.
    R-12-02 Core or stated gate / أساسي أو بوابة محددة 12 / AR Local criterion Evidence-gated expansion. New integration, synchronization or parallel coordination scope MUST identify the validated user need, authority model and maintenance owner before implementation approval.
    R-12-03 Expansion / توسع 12 / AR V-18 Evidence-bounded roadmap. Every horizon item MUST distinguish an existing capability, proposed Studio support and an uncertain forecast. Acceptance: no vendor target date becomes a Studio commitment, and no optional robotics/quantum adapter becomes an MVP dependency.
    R-13-01 Core or stated gate / أساسي أو بوابة محددة 13 / AR Local criterion Measurable evaluation. Each reported benefit MUST include its metric definition, baseline, sample, uncertainty and limitations. No mockup counts or hypothetical scenario outcomes may be entered as observed data.
    R-13-02 Core or stated gate / أساسي أو بوابة محددة 13 / AR Local criterion Correctness guardrails. Any rollout recommendation MUST satisfy the safety gates and report negative or inconclusive findings, not only favorable speed metrics.
    R-14-01 Core or stated gate / أساسي أو بوابة محددة 14 / AR Local criterion Explicit unresolved decisions. Every unresolved high-impact dependency MUST have an owner role, consequence, alternatives and gate. An implementation plan must not treat an interim position as external approval.
    R-15-01 Core or stated gate / أساسي أو بوابة محددة 15 / AR Local criterion Reviewable proposal. A reviewer MUST be able to trace a proposed behavior to its requirement, related model invariant, validation case where applicable, and supporting source or explicit design status. A favorable presentation alone is not a basis for implementation approval.
